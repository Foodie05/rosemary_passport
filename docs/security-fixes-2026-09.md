# 2026-09 安全修复兼容说明

本次变更针对安全审计中的 9 项安全问题与 2 项运维可靠性问题。

## 登录与恢复

- 无需输入账号的通行密钥登录保持不变。凭据所属用户决定登录账号；已指定账号的登录、二次验证和恢复必须使用该账号自己的凭据。
- 重复注册已有凭据会失败，不会覆盖历史公钥。
- 管理员不能仅凭邮箱、短信或验证器验证码直接重置密码。可使用经过用户验证的通行密钥恢复，或通过邮箱/手机号登录并完成二次验证后，在账户设置中修改密码。没有可用独立验证方式时，需要经过身份核验的运营恢复流程，不能通过弱化校验恢复访问。
- 登录二次验证每个挑战最多尝试 5 次，所有验证方式共享次数。耗尽后需重新开始登录。
- 密码哈希保留历史格式与参数；计算移出 HTTP 事件循环，每个服务器 isolate 同时运行 2 个任务，最多等待 16 个，超额请求返回可重试的 503。

## 应用接入

- Passport 管理接口和授权确认只接受 `first_party_web` 会话。第三方应用获得的用户令牌不等于 Passport 管理权限；`/api/v1/me` 读取继续可用。第一方 Cookie 可用于带有第三方 Bearer 的授权页面。
- `first_party_web` 为保留标识，不能通过 OIDC 授权或客户端认证发行令牌。
- 刷新令牌通过签名的 `scope` 声明保存原始授权范围，轮换时只保留或缩小范围，并检查客户端当前的刷新授权许可。响应中的 `scope` 表示实际授予范围。
- **旧版第三方刷新令牌需要重新授权一次**：它们没有记录原始授权范围，不能用客户端当前允许的全部范围进行推断。历史第一方刷新会话保留已知的默认范围。既有数据库迁移和历史凭据未改写。
- 通用资料更新中的 `new_email` 现在返回 `email_verification_required`。客户端应使用已有的发送绑定验证码和绑定邮箱接口验证新地址。第一方 Web 已使用该流程。ID Token 的 `email_verified` 取自账户的实际验证状态。

## 本地开发与运维

- 开发 PostgreSQL 仅监听 `127.0.0.1:5432`；新环境使用独立随机密码。`run_local.sh` 会为仍使用历史默认密码的本地数据库执行密码轮换，再更新本地 `.env`。已有自定义密码及 PEM 配置迁移时的数据库密码会保留。
- 手工操作根目录 Compose 时使用 `docker compose --env-file apps/passport_server/.env ...`，或显式提供 `DB_PASSWORD`。不要通过删除数据库卷来升级。
- PITR 演练从实际的 `user_roles` 表统计角色，证据字段仍称为 `roles`。
- SLA 评估先验证完整签名哈希链，再评估最近指定天数；第 15 天起仍可评估最近 14 天。窗口外的篡改仍会失败，窗口外已经签名的失败观察不会使新的完整通过窗口永久失败。

上线前仍须在部署环境完成生产镜像、实际通行密钥设备、恢复演练和容量验收；本地测试结果不等于生产 SLA 承诺。
