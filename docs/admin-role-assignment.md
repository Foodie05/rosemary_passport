# 管理员角色分配

当前允许角色由 `AuthenticatedUser.allowedRoles` 定义，为 `user` 和 `admin`。管理页的用户列表响应新增 `supported_roles`，供创建和编辑用户时的角色复选控件使用；不再输入逗号分隔文本。至少保留一个受支持角色。

`PATCH /api/v1/admin/users/{id}/roles` 和管理端创建用户的 `POST /api/v1/admin/users` 均要求第一方管理会话、当前有效的 `admin` 权限，以及本次请求携带的 MFA 证明。创建时分配角色同样验证，避免绕过编辑接口直接授予管理员权限。

```json
{
  "roles": ["user", "admin"],
  "verification": {"method": "email_code", "code": "123456"}
}
```

示例码仅用于本地合成验收。可选 `method` 为 `email_code`、`phone_code`、`authenticator` 或 `passkey`，必须是当前管理员已绑定且仍可用的方式。密码和空证明不满足 MFA。验证码通过现有 `/api/v1/me/step-up/send-code` 获取；通行密钥通过 `/api/v1/me/step-up/webauthn-options` 获取挑战，并在 `verification.response` 中提交签名响应。使用同一已有校验服务，保持验证码用途/时效/消费、频控和通行密钥用户验证要求，不新增缓存的“已验证”布尔开关。

验证针对会话中的操作管理员，不针对目标用户，不接受请求体伪造的操作者 ID。普通用户或被封禁管理员返回 403；缺少 MFA 或校验失败不得写入角色，也不记录成功审计。编辑中的草稿取消后不提交；校验失败保留角色选择并清除证明，成功后关闭弹窗并刷新列表。更改自己的角色后立即更新当前管理界面的权限状态。

角色写入事务按固定次序锁定操作者与目标用户，重新查询当前管理员角色和有效账户状态。因此在 MFA 期间或并发请求中已被撤销管理员权限的操作者不能继续写入；创建账户时也在写入事务内复查。无数据库结构迁移，不回填或重写既有用户、凭据和角色。成功审计只增加验证方式名称，不记录验证码、密码或通行密钥响应。

本次同时调整账户页：资料三行左对齐；登录与验证、联系与恢复各共用一个容器，无逐行色差；移除安全提示及账户角色侧栏。用户表在窄屏中将长昵称、邮箱和手机号显示为单行省略，完整文本保留在 title、可访问名称与详情入口中。

验证包括 Web 选择/证明负例、角色路由的权限与 MFA 测试，以及独立 PostgreSQL 中成功写入、撤权、封禁、创建赋权、目标不存在和并发撤权回归。浏览器仅操作本地合成用户与测试验证码，不连接生产库或使用真实 MFA 凭据。

认证页另按产品要求取消整条顶栏，将较小 Logo 和明暗切换放在左右上角。登录、注册、恢复仅用圆角容器包覆右侧表单，保留四周外边距；左侧文案和图案直接置于页面背景，Logo、左侧内容与版权文字共用同一左基线。右上角明暗切换与底部链接组对齐圆角容器右侧外边沿，表单控件保留容器内边距，页脚无分割线。

登录与注册协议说明使用 SDK Checkbox 的 label 插槽：普通说明、连接词和版本文字均可勾选；协议链接独立打开，不改变勾选。保留原生空格键和禁用行为。

本地验证：Web 69 项测试及生产构建通过；后端分析及隔离 PostgreSQL 下 169 项可见测试通过，无跳过。浏览器验证 1440px 桌面与 320px 窄屏、明暗主题、资料对齐与合并列表、角色 MFA 失败及成功路径，以及说明文字/版本文字/空格键勾选与协议链接互不干扰。
